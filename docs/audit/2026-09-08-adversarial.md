# Adversarial audit — 2026-09-08

Twelve independent finder agents over the safety-critical surfaces of `main` (ca374cb), each finding
then put to three skeptics with different lenses — does the code really do this, can anyone actually
reach it, and does a test already cover it. A finding survived only when fewer than two skeptics
refuted it. 124 raw findings, 110 reached a verdict, 85 survived. The run stalled before its final
synthesis; these are recovered from the run journal, so the counts below are what each finding
actually received, not an estimate.

**How to read `refuted`.** `0/3` means no skeptic could refute it. `1/3` means one could — those are
worth re-reading before acting, not worth dismissing.

**Threat model.** ao concedes in `docs/safety.md` that a process running as the same user cannot be
cryptographically excluded, only detected. Findings that merely restate that are marked below; they
still matter, because detection is the guarantee that remains and several of them weaken it.

### `src/ao/cli.py:653` — commit-ok's "reviewer is the implementer" check compares the review's free-text label against implementer.session, so a review the implementer wrote about itself is accepted

*lens: reviewer-independence · refuted 1/3*

**Guarantee broken.** docs/safety.md §4b: "commit-ok refuses when ... the reviewer is the implementer", and docs/roles.md: "`ao` refuses that assignment rather than warning about it." The whole check is `rwho = re.search(r"reviewer:\s*`([^`]+)`", rbody)` (cli.py:648-649) compared to `impl_id = (cfg.get("implementer") or {}).get("session") or ""` (cli.py:650) via `rwho in impl_id or impl_id in rwho` (cli.py:653). It reads only `implementer.session` — never `adapter`, `name`, or `model` — and compares it to a label chosen by whoever wrote the review file. Those two namespaces do not collide in any shipped configuration (`_apply_profile` writes `session: "auto"` and a reviewer `id` of `claude-reviewer-<model>`; `discover_session` supplies an opaque uuid), so the check cannot fire.

**Sequence.** 1. Implementer stages its work: `git add src/a.py`. 2. It runs `git rev-parse HEAD`, `git write-tree`, `git diff-tree -p --binary --full-index --no-ext-diff --no-renames --no-commit-id HEAD <tree> --` and reproduces `index_candidate`/`candidate_scope`/`diff_digest` byte for byte — all public, deterministic, no secret. 3. It writes `semantic-review/forged.md` with that evidence line, `- reviewer: `kiro``, `VERDICT: APPROVED`, `BLOCKER: 0 / HIGH: 0 / MEDIUM: 0 / LOW: 0`. `semantic-review/` is a coordination path (lib.py:1288), so the new file trips none of `candidate_worktree_issues`. 4. `ao verify` passes on that exact candidate. 5. `ao commit-ok` → cli.py:648 extracts rwho="kiro"; cli.py:653 asks whether "kiro" is a substring of "s1" or vice versa; it is not → GRANTED. 6. `git commit` → the pre-commit `ao commit-check` re-reads the same file and prints AUTHORIZED. The implementer has committed on a review it wrote about itself, which is the exact failure §4b claims was fixed.

**Evidence.** Ran against the repo's own `project` fixture (implementer `{adapter: kiro, session: s1, name: kiro}`). The implementer writes `semantic-review/forged.md` itself, containing a schema-2 evidence line whose `candidate`, `scope` and `diff_digest` it computed from git, plus `- reviewer: `kiro`` — the implementer's own adapter and name — and `VERDICT: APPROVED`. `cmd_commit_ok` printed GRANTED (exit 0), the authority row recorded `granted: true, reviewer: "kiro"`, and `cmd_commit_check` (the pre-commit path) printed AUTHORIZED. The repo's own `tests/test_commit_authority.py::test_commit_ok_records_the_exact_index_candidate` already demonstrates the same thing with `_write_approved_review`, a file no reviewer process ever produced. Nothing in `latest_candidate_review` (lib.py:1584) or `candidate_review_integrity` (lib.py:1535) distinguishes an artifact `ao review` wrote from one the implementer wrote; `cmd_review` appends no ledger row (only best-effort `notices.jsonl`, lib.py:1043, which commit-ok never reads).

### `src/ao/cli.py:2949` — In a linked git worktree ao installs both hooks where git never looks, then reports them installed

*lens: authority-grant · refuted 0/3*

**Guarantee broken.** PRE_COMMIT_HOOK (cli.py:2922) plus safety.md ("`ao commit-check` is the non-mutating enforcement half: the optional AO pre-commit hook runs it against Git's active index") and safety.md §2 ("Write lanes get separate git worktrees"). `_ao_hook_paths` computes `hooks = os.path.join(A.sh("git rev-parse --git-dir", cwd=root) or ".git", "hooks")`. Git resolves hooks from `core.hooksPath` if set, otherwise from `$GIT_COMMON_DIR/hooks` — never from a linked worktree's own `--git-dir`. So in exactly the topology AO mandates for write lanes, `ao hooks install` writes pre-commit and pre-push into `.git/worktrees/<lane>/hooks/`, which git never executes.

**Sequence.** 1. Main repo at $T/main; a write lane created the way safety.md §2 requires: `git worktree add ../lane -b lane`. 2. In the lane: `ao -C $T/lane hooks install` -> prints "installed pre-commit -> revalidates the recorded grant; pre-push -> requires a recent human push window". Files land in $T/main/.git/worktrees/lane/hooks/{pre-commit,pre-push}; $T/main/.git/hooks (the dir git actually consults, = GIT_COMMON_DIR/hooks) stays empty. 3. `ao -C $T/lane hooks status` prints "pre-commit: installed / pre-push: installed"; `ao -C $T/lane doctor` prints "commit hook installed / push hook installed" in green. 4. In the lane, with no `ao verify`, no review and an authority ledger that has never been written: `echo x > g.txt; git add g.txt; git commit -m 'unauthorized commit, no grant at all'` -> commit lands. No `ao commit-check` ran, no --no-verify, no ledger or config tampering. 5. `git push` from the lane is likewise unguarded, since pre-push is in the same dead directory. Same defect with `core.hooksPath` set (husky / pre-commit framework): `git config core.hooksPath .husky` then `ao hooks install` writes to .git/hooks, reports installed, and git runs .husky/ instead.

**Evidence.** Ran the sequence end to end against this worktree's .venv. `git rev-parse --git-dir` in the lane = /…/main/.git/worktrees/lane while `--git-common-dir` = /…/main/.git (git 2.50.1). Commit "unauthorized commit, no grant at all" landed with the AO hooks present in the per-worktree hooks dir; a hand-written pre-commit in the same dir that does `exit 1` also failed to block a commit, confirming git never runs it. `ao doctor` output: "commit hook installed / push hook installed". Control: in a normal single-worktree repo the same install works and `ao commit-check` correctly refused a commit whose index had drifted from the grant. tests/test_switches_and_bypass.py:150-170 only ever exercises `os.path.join(root, ".git", "hooks")`, and no source file in src/ao mentions linked worktrees or core.hooksPath.

### `src/ao/cli.py:1645` — "Verdict contradicts its own findings" downgrade never reaches the persisted review, so commit-ok grants on a review with BLOCKERs

*lens: authority-grant · refuted 0/3*

**Guarantee broken.** cli.py:1643 states the rule: "A verdict that contradicts its own findings is not a verdict." The guard is `if verdict == "APPROVED" and (sev["BLOCKER"] or sev["HIGH"]): verdict = "NEEDS_CHANGES"` — it rebinds a local only. The artifact is then written as `"\n".join(header) + f"\n\n{out}\n"` (cli.py:1706) with the reviewer's untouched `out`, so the file on disk still reads `VERDICT: APPROVED`. `evidence["authorizable"]` is likewise left True. The parallel guard 19 lines below (candidate changed during review, cli.py:1660-1668) does the right thing: it sets `authorizable=False` and rewrites `out` with `re.sub(r"VERDICT:\s*APPROVED", "VERDICT: NEEDS_CHANGES", out, count=1)`. Authority reads the file, not the local: `A.reviews()` re-parses `VERDICT:` from the body, `latest_candidate_review` accepts it because verdict == "APPROVED" and authorizable is True, and `cmd_commit_ok` grants.

**Sequence.** 1. Implementer stages src/a.py and runs `ao review --boundary "..."`. 2. The independent reviewer answers `VERDICT: APPROVED / BLOCKER: 2 / HIGH: 1 / MEDIUM: 0 / LOW: 0` with two [BLOCKER] findings ("hardcoded credential added", "auth check removed") — an ordinary LLM-reviewer self-contradiction, which is why the guard exists. 3. AO prints yellow `NEEDS_CHANGES  BLOCKER 2 · HIGH 1`, writes notices.jsonl "NEEDS_CHANGES {'BLOCKER': 2, ...}", and tells the implementer not to commit — but semantic-review/<file>.md contains `VERDICT: APPROVED` and evidence with `"authorizable":true` bound to the exact candidate. 4. `ao verify` passes. 5. `ao commit-ok` -> GRANTED, naming that review file. 6. `git commit` -> the pre-commit hook's `ao commit-check` prints AUTHORIZED and the commit lands. Code the independent reviewer flagged with two BLOCKERs is committed under a valid, chained authority grant. No tampering: every artifact was produced by ao itself.

**Evidence.** Reproduced with a scripted reviewer emitting exactly that output. Console: "NEEDS_CHANGES  BLOCKER 2 · HIGH 1 · MEDIUM 0 · LOW 0"; artifact tail: "VERDICT: APPROVED / BLOCKER: 2"; `A.reviews(root,'semantic-review')` -> [(file,'APPROVED')]; `ao commit-ok` -> "GRANTED C-1788823868053279000"; `git commit` -> "AUTHORIZED 6b4d8c2f… · C-1788823868053279000" and commit 57ef431 "landed despite 2 BLOCKERs". notices.jsonl recorded NEEDS_CHANGES for the same review. `grep -rn 'contradict|BLOCKER: 2' tests/` returns nothing — no test covers this path. The same hole exists in strict mode: nothing on this branch sets `evidence["authorizable"] = False` or touches `review_status`.

### `src/ao/cli.py:2924` — A second process can stage unreviewed paths after `ao commit-check` passes and they land in the authorized commit

*lens: concurrency · refuted 1/3*

**Guarantee broken.** PRE_COMMIT_HOOK is `exec {ao} -C {root} commit-check` and is documented as the point where "commit authority is bound to Git's exact active index"; ADR 0002 says `ao commit-check`, "including the optional pre-commit hook boundary, revalidates the live active index against that grant immediately before Git proceeds". The ADR's stated limitation is scoped only to "the hook is not installed or another commit path bypasses it" — it does not cover a mutation of the index while the hook is installed and the normal commit path is used.

**Sequence.** 1. Implementer stages a small, innocuous candidate D1 (e.g. one doc line). 2. `ao review` -> reviewer APPROVES D1; `ao verify` passes on D1; `ao commit-ok` -> GRANTED for D1, ledger row records candidate D1. 3. Implementer starts a background process (any shell job it spawns) that busy-waits and then runs `git add src/ao/lib.py` (unreviewed edits already written to the worktree). 4. Implementer runs `git commit -m ...`. The pre-commit hook runs `ao commit-check`, measures the index, sees exactly D1, prints AUTHORIZED and exits 0. 5. The background process stages the unreviewed file in the tens-of-milliseconds window after the hook exits. 6. Git re-reads the index and commits D1 + the unreviewed file. The commit lands; the authority ledger says only D1 was ever approved; nothing detects the difference. The same sequence happens accidentally whenever two turns are live in one tree (the exact hazard `child_alive` documents): an honest implementer's commit silently absorbs the other turn's half-finished edits.

**Evidence.** Read cmd_commit_check (src/ao/cli.py:706-800) — it compares A.index_candidate(root) to grant['candidate'] and exits non-zero on mismatch, but it is a pre-commit hook, so it returns before git computes the tree. Verified empirically in a throwaway repo (scratchpad, not the reviewed repo): with a pre-commit hook that only validates and exits 0, a `git add evil.txt` issued by a SEPARATE process after the hook exited was included in the commit in 6 of 6 timed runs (delays 0.300s-0.340s against a 0.300s hook), and in 1 of 3 runs with a naive fixed 40ms delay. Git re-reads the index after pre-commit (this is why formatter hooks that `git add` work), so the tree git writes is not the tree the hook validated. There is no post-commit reconciliation anywhere in the codebase: `grep -rn index_tree src/ao/` shows the granted tree object is never compared against what actually landed.

### `src/ao/features.py:53` — A torn config write erases the strict capability_matrix opt-in, silently downgrading commit authority to legacy

*lens: durability · refuted 0/3*

**Guarantee broken.** load_config (src/ao/lib.py:126-134) states: "Once the strict key is present, however, a parse failure must not erase the opt-in and silently reactivate legacy authority", and _has_top_level_json_key (src/ao/lib.py:60) claims to "Recognize a top-level JSON object key even when the document is truncated" because "Config parse failure cannot be allowed to erase an opt-in authority boundary". That guard only works on the surviving byte *prefix*. Every writer of .ao/config.json (features.py:53, cli.py:2044) is a truncate-in-place `json.dump(cfg, open(p, "w", ...))`, and the overwhelmingly likely crash outcome is a zero-byte file, for which the guard cannot fire.

**Sequence.** 1. Project has capability_matrix in .ao/config.json; strict authority is in force. 2. Anyone runs `ao features nudge off` (features.set_switch, features.py:51-53). `open(p, "w")` truncates config.json to zero bytes before json.dump emits a byte. 3. The process is SIGKILLed / the laptop dies / the flush fails with ENOSPC. config.json is now 0 bytes. 4. Next `ao commit-ok`: load_config catches the parse failure, _has_top_level_json_key(b"") is False, so cfg = {} and M.is_strict(cfg) is False. commit-ok skips M.resolve, skips M.review_evidence_problems, and records a schema-2 grant instead of schema-3. 5. The pre-commit hook runs `ao commit-check`: it is also non-strict, its only strict-drift guard is `grant.get("schema") == 3 or grant.get("matrix") is not None`, which is False for the fresh schema-2 grant, so it authorizes the commit. No output anywhere says the capability matrix vanished. 6. Aggravating: if the operator then re-runs `ao init --profile ...`, _apply_profile (cli.py:2015-2019) falls back to `cfg = {}` on the unreadable file and rewrites config.json with only implementer/reviewer/architect (cli.py:2044), destroying the original bytes permanently. Note the contrast: a *non-empty* malformed config that still contains the key raises MatrixError and refuses loudly. Whether the tool fails safe or fails open is decided purely by where the truncation landed.

**Evidence.** Ran against the repo venv: with a healthy strict config, M.is_strict(A.load_config(d)) is True. After simulating the crash window by `open(p,"w").close()` (exactly what json.dump does before it writes anything), A.load_config returns only {'root','mailbox','reviews'}, M.is_strict is False, and A._has_top_level_json_key(b"", "capability_matrix") returns False. A prefix truncated before the capability_matrix key gives the same result. Read cmd_commit_ok (cli.py:548) and cmd_commit_check (cli.py:709): both take `strict = M.is_strict(cfg)` and nothing else re-derives the opt-in.

### `src/ao/lib.py:2433` — A NEEDS_CHANGES review is read as APPROVED and grants commit authority

*lens: review-evidence · refuted 0/3*

**Guarantee broken.** docs/safety.md §3 promises a grant only when "the newest structured prospective review for that candidate is APPROVED". The verdict is never carried in the structured evidence — `review_evidence_line` writes `authorizable`, `candidate`, `scope`, `diff_digest` but no verdict — so the whole gate rests on `reviews()`: it takes the FIRST line whose lowercase text contains "verdict" and does `re.sub(r".*:\s*", "", line)`, a greedy match that keeps whatever follows the LAST colon on that line. `latest_candidate_review` (lib.py:1606) then compares that string to "APPROVED", and neither `candidate_review_integrity` (lib.py:1541) nor `matrix.review_evidence_problems` (matrix.py:511) looks at the verdict at all — so strict mode does not catch it either.

**Sequence.** Trigger A (implementer-controlled, deterministic): the implementer stages its candidate under src/ao and runs the ordinary review command with a crafted scope: `ao review --paths 'verdict:/../src/ao' 'zz/../: APPROVED'`. `--paths` is a real flag (cli.py:3674) and `_normal_scope_paths` normpaths both arguments to `src/ao` and `: APPROVED`, so the evidence JSON, the scope digest and the diff digest are all legitimate and contain no "verdict". But cli.py:1709 writes the RAW argv into the header: `- paths: verdict:/../src/ao zz/../: APPROVED`. That header line precedes the reviewer's own `VERDICT: NEEDS_CHANGES` in the file, it is the first line containing "verdict", and the greedy sub yields exactly "APPROVED". The independent reviewer rejects with a BLOCKER; `ao commit-ok` grants anyway; `ao commit-check` (the pre-commit hook half, cli.py:794) re-runs the same reader and AUTHORIZES. Trigger B (no flags needed): any reviewer output that contains a mixed-case line such as `## Verdict summary: APPROVED` before its canonical `VERDICT: NEEDS_CHANGES` line — cmd_review's own parser at cli.py:1583 is case-SENSITIVE on `VERDICT:` and correctly records NEEDS_CHANGES, while `reviews()` is case-INSENSITIVE and reads APPROVED from the earlier line. Verified: GRANTED with the artefact reading `VERDICT: NEEDS_CHANGES / BLOCKER: 1`. The same divergence fires on a single canonical line with a trailing clause, e.g. `VERDICT: NEEDS_CHANGES — the prior round was: APPROVED`.

**Evidence.** Ran `cli.cmd_review` against a fake reviewer that emits `VERDICT: NEEDS_CHANGES / BLOCKER: 1`. cmd_review printed NEEDS_CHANGES and returned 1; the artefact contains `VERDICT: NEEDS_CHANGES` and `authorizable":true`. `A.reviews()` returned `('...md', 'APPROVED')`, `latest_candidate_review` returned that artefact, `candidate_review_integrity` returned `[]` reasons, and `cli.cmd_commit_ok` printed `GRANTED  C-1788823415917982000` (rc 0). Two independent triggers reproduce it.

### `src/ao/lib.py:3574` — A lost `close_waiver` append permanently re-opens the review bypass, and `ao catchup` reports success anyway

*lens: durability · refuted 1/3*

**Guarantee broken.** `close_waiver` is the ONLY thing that ever retires a review waiver (`open_waivers` has no expiry), and it is the whole basis of `cmd_waive`'s promise: "commit-ok honours it; `ao catchup` runs the missed review against the landed range and closes it." But the close row is written with a plain buffered `with open(..., "a")` — no lock, no fsync, no tail repair — and any OSError is swallowed by `except OSError: pass` (src/ao/lib.py:3579-3580). The reader `open_waivers` (src/ao/lib.py:3583) silently `continue`s past any line that will not parse. Meanwhile `cmd_commit_ok` (src/ao/cli.py:614-620) treats an open review waiver as a total bypass: `elif waiver: print("review waived ...")` adds NO entry to `reasons`, in strict mode too, so a full commit grant is recorded and the pre-commit hook honours it with no independent reviewer anywhere in the chain.

**Sequence.** 1. Reviewer is out of quota; a human runs `ao waive review --why ...`. `waive()` defaults slice to `*` (cli.py:2856), which matches every slice in commit-ok's lookup. 2. The implementer lands several commits; each `ao commit-ok` prints "review waived by human (W-1)" and records a granted authority row with no review. 3. The human runs `ao catchup`. `cmd_review` returns 0, so cli.py:2879 calls `close_waiver(root,'W-1','reviewed: APPROVED')`. 4. That append is lost — either it merges into a torn tail left by an earlier crash mid-append (waivers.jsonl is never repaired and no writer holds a lock), or it raises OSError on a full/read-only volume and is swallowed. 5. `ao catchup` prints "catchup handled 1 item(s)" and exits 0. The operator believes the bypass is closed. 6. Every subsequent `ao commit-ok` still finds W-1 open and grants commit authority with the review gate off, indefinitely — the implementer commits without any independent reviewer, which is the exact thing the program exists to prevent.

**Evidence.** Ran two reproductions against the repo venv. (a) Torn-tail merge: waivers.jsonl = one good `waived` W-1 row + a torn `{"event":"waived","id":"W-2","gate":"revi` tail with no newline; `A.close_waiver(root,'W-1','reviewed: APPROVED')` appended onto that tail, producing one unparseable line; `A.open_waivers(root, gate='review')` then returned `['W-1']` — the close vanished. (b) Write failure: with waivers.jsonl mode 0444, `A.close_waiver(...)` swallowed the OSError and returned normally; `open_waivers` still returned `['W-1']`. In both cases cli.py:2879 does `A.close_waiver(...)` then `did += 1` and prints "catchup handled 1 item(s)".

### `src/ao/lib.py:133` — An empty or early-truncated .ao/config.json silently drops strict capability-matrix authority back to legacy authority

*lens: authority-grant · refuted 1/3*

**Guarantee broken.** lib.py:130-134 states: "Once the strict key is present, however, a parse failure must not erase the opt-in and silently reactivate legacy authority", and `_has_top_level_json_key` is documented as recognizing the key "even when the document is truncated". It records a schema-2 grant. 5. `cmd_commit_check` also sees `strict = False`; its guard at cli.py:747-750 ("capability_matrix was removed after this strict authority grant") only fires for a pre-existing schema-3 grant, so the new schema-2 grant passes and the commit is AUTHORIZED. 6. Nothing prints a warning and `ao doctor` still shows `config .ao/config.json` in green. The declared capability matrix — the only mechanism that actually enforces reviewer independence — is gone and no output says so.

**Evidence.** Ran `A.load_config` + `M.is_strict` on a temp project with a strict config: intact -> strict True; truncated 30 bytes past the key -> strict True with `_capability_matrix_error` set (fails closed, correct); truncated just before the key -> strict False; zero-byte file -> strict False, `reviews` silently reverts to the default "semantic-review" and `features.enabled(cfg, 'review')` returns the default True; file removed -> strict False. `features.set_switch` (features.py:50-53) writes the config as `json.dump(cfg, open(p, "w", ...))` — `open(p, "w")` truncates to zero bytes before anything is written, there is no temp-file+rename and no fsync. `ao doctor` (cli.py:3436) only tests `os.path.exists`, so it still prints the config in green.

### `src/ao/cli.py:1430` — Non-strict reviewer independence is a no-op; a fallback reviewer may be the implementer's own engine

*lens: review-evidence · refuted 1/3*

**Guarantee broken.** docs/safety.md §4 says "`reviewer ≠ implementer` for the same slice, enforced rather than advised" and "the reviewer must at least run a different model family", and cmd_review's own docstring (cli.py:1404) says "commit-ok refuses a review whose author is the implementer". ### `src/ao/watchdog.py:721` — parse_reset can only express resets measured in hours, so a weekly or monthly limit becomes a one-hour block and a wrong 'until' time shown to the human

*lens: clock-and-quota · refuted 0/3*

**Guarantee broken.** `WAKE_SIGNATURES` (watchdog.py:708) deliberately matches `hit your (?:session|usage|weekly|monthly) limit`, and `wake_error`'s docstring says "a *quota* wants a wait until `resets_at`".
