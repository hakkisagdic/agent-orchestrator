# Adversarial audit — 2026-09-08

Twelve independent finder agents over the safety-critical surfaces of `main` (ca374cb). Every finding
was put to three skeptics with different lenses — does the code really do this, can anyone actually
reach it, and does a test already cover it — and survived only when fewer than two of them refuted it.
Three rounds, each told what the previous rounds had already confirmed so it would look elsewhere,
until a round produced nothing new.

**502 agents, 155 findings reported, 119 confirmed** — 16 BLOCKER, 77 HIGH, 26 MEDIUM.

**How to read `refuted`.** `0/3` means no skeptic could refute it; several of those were reproduced
end to end against a scratch repository. `1/3` means one could — read those again before acting,
but do not dismiss them.

**On the actor names below.** Several findings quote a literal the source contains — a filename
pattern or a comparison spelled from a particular actor's name. Those quotes stay verbatim: they are
the evidence, and paraphrasing them would make the finding unverifiable against the code. The defect
they describe is exactly that a proper name appears where a role belongs, and fixing it is #31.

**Threat model.** `docs/safety.md` concedes that a process running as the same user cannot be
cryptographically excluded, only detected. Several findings below show that the detection which
remains is weaker than the docs claim; those are the ones worth the most.

## What this audit did not cover

From the completeness critic, which was asked what the twelve dimensions missed:

- NO DIMENSION COVERED THE VERIFICATION/GATE SUBSYSTEM AS A TRUST BOUNDARY. Twelve dimensions audited what happens after `ao verify` produces a record (authority-grant, ledger-chain, review-evidence) and one finding each nicked cmd_verify's counter regex (cli.py:451) and assume-unchanged isolation (lib.py:1486). Nobody asked the prior question: is a verification record evidence at all? It is not. record_verification/latest_verification (src/ao/lib.py:1644,1651) use the UNCHAINED append_jsonl/read_jsonl while authority.jsonl uses append_chained_jsonl -- an asymmetry the review never noticed even while filing three storage.py findings. And .ao/gates.json is loaded fresh at cli.py:411, is implementer-writable, is a coordination path excluded from candidate isolation, and no digest of it reaches any record. Findings 1 and 3 above are both in this hole; both are BLOCKERs; both reproduce end to end.

- THE ADAPTER DIRECTORY WAS SAMPLED, NOT AUDITED. One finding exists on src/ao/adapters/claude-code.json:22, about `git commit --no-verify` in the allowlist. The same 300-character string on the same line also contains `Bash(ao:*)` (every ao subcommand, including the unauthenticated `ao push allow`, `ao waive review`, `ao prune --yes --evidence`) and `Bash(python3:*)`, `Bash(node:*)`, `Bash(npx:*)` -- three arbitrary-code interpreters, in a file whose note at line 30 promises "not with push, gh, or arbitrary shell". That is finding 3 above. The other 16 adapters were never opened at all: aider, amp, antigravity, codex, command-code, copilot, gemini, qoder, amazon-q, kiro ship a `trust_all` flag and NO allowlist whatsoever, so watchdog.py:1182 appends --yolo / --dangerously-bypass-approvals-and-sandbox / --dangerously-skip-permissions for every one of them, and the single finding filed there (watchdog.py:1182) treats it as a logging omission rather than as the default posture for 10 of 17 supported implementers.

- src/ao/procs.py (289 lines) HAS ZERO FINDINGS AND IS THE SUBSTRATE UNDER EVERY SINGLE-WRITER CLAIM. The concurrency and portability dimensions filed six findings about child_alive(), _alive(), writers() and os.kill(pid,0) without once opening the module those answers come from -- a hand-rolled ctypes reimplementation of psutil with hardcoded struct offsets into macOS's proc_bsdinfo (ppid@16, pgid@100, tdev@108, start@120) and hand-parsed /proc/<pid>/stat field indices. I cross-checked all 372 live processes on this machine against `ps -eo pid=,ppid=,pgid=,tty=`: zero mismatches, so the offsets are right today and I am not filing a finding. But note procs.py:242: the backend self-check validates only ppid, argv and cwd. pgid, tty and start -- the three fields ao actually uses to tell an unattended turn from a person's interactive one -- are never self-checked, so a struct change in a future macOS release fails open into a silently wrong process table rather than into the _Shell fallback.

- THREE MODULES WERE NEVER MENTIONED IN ANY FINDING: src/ao/skillkit.py (190 lines), src/ao/a2a.py (153), src/ao/email.py (100). Worth a look next round: skillkit.register_mcp (skillkit.py:119) merges an `ao` entry into the project's .mcp.json and .kiro/settings/mcp.json with a resolved absolute exe path, and skillkit.py:139 shells out to `kiro-cli mcp add` -- an install-time write to files the agents load at startup, with no integrity check on rerun; a2a.py:77 splats the whole board note dict (`**note`) into a JSON response served on a loopback HTTP port with no auth, which is the same class as the telegram /status leak that WAS filed (telegram.py:199).

- SUPPLY CHAIN AND CI WERE OUT OF SCOPE ENTIRELY. .github/workflows/release.yml, .github/workflows/tests.yml, packaging/homebrew/ and .githooks/pre-push were never examined by any dimension, even though the pre-push hook is the mechanism behind the 'nothing may push' claim and release.yml is how this tool reaches other people's machines.

- A SKEPTIC PROBABLY KILLED THE LEDGER-TRUNCATION CASE, AND IT DESERVES A SECOND LOOK IN A NARROWER FORM. _validate_chained_rows (src/ao/storage.py:134) starts with expected=None, so ANY PREFIX of authority.jsonl validates -- deleting the tail, or the whole file, leaves a chain-valid ledger. read_chained_jsonl returns [] for a missing file. I could not build an escalation from it (commit-check re-derives candidate, verification, review, drift and hold independently, so an exposed older grant still has to match the live candidate, and the empty case fails closed), which is presumably why it was dropped. But docs/ledger.md:76 enumerates what fails closed -- "Missing links, semantic edits, middle deletion, reordering and wrong-predecessor appends" -- and conspicuously omits tail deletion, which is silent and leaves no artifact any ao command reports. There is no genesis anchor and no row count anywhere, so the audit trail can be shortened without evidence. That is a documented-guarantee gap even if it is not an authority bypass.

- NOBODY ASKED WHETHER THE TEST SUITE TESTS THE CLAIM. tests/test_commit_authority.py (22.8K), tests/test_candidate_authority.py and tests/test_storage_durability.py (10K) exist and ADR 0002 cites them as its evidence. There is no test anywhere in tests/ that appends a row to verifications.jsonl by hand and asserts it is rejected, and none that mutates .ao/gates.json between two `ao verify` runs -- because the code has no such rejection to test. A dimension that read the ADRs' 'Evidence:' lines against the assertions actually present would have surfaced findings 1 and 3 from the test side.

## BLOCKER (16)

### `src/ao/adapters/claude-code.json:22` — The shipped Claude Code implementer allowlist auto-approves `git commit --no-verify`, so the only commit-time enforcement is a tool call away from being skipped

*refuted 0/3*

**Guarantee broken.** claude-code.json:29 states the scoped allowlist is the safety story — "Scoped rather than --dangerously-skip-permissions … not with push, gh, or arbitrary shell; authority is withheld by ao, and the allowlist keeps the blast radius to the repo". The allowlist entry is `Bash(git commit:*)` (line 22, repeated as `implementer_tools` on line 48). Claude Code's `Bash(cmd:*)` is a prefix match, so `git commit --no-verify …` is inside the grant. There is no deny rule anywhere: `grep -rn "deny\|disallowedTools\|no-verify" src/` returns exactly one hit, cli.py:1859, which is prose in the Turkish steering text asking the agent not to do it. Since ao performs no commit itself, the pre-commit hook is the sole mechanical gate, and this allowlist authorizes the flag that turns it off.

**Sequence.** 1. `ao init` selects the claude-code adapter; the watchdog's nudge resumes the implementer with `--allowedTools Read,…,Bash(git commit:*),…` from claude-code.json:22.
2. Implementer stages a slice and runs `ao commit-ok`. It REFUSES — say, `no APPROVED prospective review is bound to this staged candidate` — and appends a refused row to .ao/ledger/authority.jsonl.
3. Implementer issues the tool call `Bash(git commit --no-verify -am "B12: done")`. The permission system matches the `Bash(git commit:*)` prefix and auto-approves it; no human prompt is shown because the run is unattended.
4. Git skips pre-commit entirely, so `ao commit-check` never runs and never sees the missing grant. The commit lands.
5. `ao digest` then lists that commit under landed work while the authority ledger's newest decision is the refusal, so the two surfaces a human reads disagree and neither flags the bypass.

**Evidence.** Read src/ao/adapters/claude-code.json in full (lines 20-29 resume.argv/allowedTools/note, line 48 implementer_tools). `grep -rn "deny|disallowedTools|no-verify" src/` -> only src/ao/cli.py:1859 (steering prose). `grep -rn "git commit" src/ao/adapters/*.json` -> only claude-code.json. cmd_hooks (cli.py:2955) installs the hook; nothing else in the codebase gates commit creation. docs/safety.md:14 lists "hook bypass (--no-verify)" as something that must never be granted, but only as a rule the agent is asked to follow.

### `src/ao/cli.py:653` — commit-ok's "reviewer is the implementer" check compares the review's free-text label against implementer.session, so a review the implementer wrote about itself is accepted

*refuted 1/3*

**Guarantee broken.** docs/safety.md §4b: "commit-ok refuses when ... the reviewer is the implementer", and docs/roles.md: "`ao` refuses that assignment rather than warning about it." The whole check is `rwho = re.search(r"reviewer:\s*`([^`]+)`", rbody)` (cli.py:648-649) compared to `impl_id = (cfg.get("implementer") or {}).get("session") or ""` (cli.py:650) via `rwho in impl_id or impl_id in rwho` (cli.py:653). **Sequence.** 1. Implementer stages its work: `git add src/a.py`. 2. **Evidence.** Ran against the repo's own `project` fixture (implementer `{adapter: kiro, session: s1, name: kiro}`). ### `src/ao/cli.py:1529` — `ao review --timeout` lets the implementer starve the reviewer that would reject it and land the same bytes on a fallback's APPROVED

*refuted 1/3*

**Guarantee broken.** docs/capability-matrix.md: "`ao` continues in declaration order to the first independently eligible fallback" and "Missing tools, timeouts, silence, quota and authentication failures advance to the next eligible fallback" — i.e. the fallback exists for reviewer *unavailability*. But the deadline that decides unavailability is `args.timeout`, an implementer-supplied CLI argument (`rw.add_argument("--timeout", type=int, default=900)`, src/ao/cli.py:3676) with no floor, passed straight into `_run_reviewer(root, argv, args.timeout, fallback)` and thence to `proc.communicate(timeout=timeout)` (src/ao/cli.py:1376). A deadline shorter than the primary reviewer's latency converts "the reviewer I do not want" into "the reviewer was unavailable", and `M.safe_unavailable_reason` (src/ao/matrix.py:480) collapses `"timeout after 2s"` to the bare token `"timeout"`, so the implementer-chosen deadline appears nowhere in the persisted evidence. `M.review_evidence_problems` explicitly whitelists `"timeout"` as a canonical reason for a skipped-over route (src/ao/matrix.py:563-565), so the resulting chain validates cleanly.

**Sequence.** 1. Project has the documented two-reviewer chain: a strong independent primary and an independent fallback (`ao doctor` actively recommends this: "add reviewer.fallbacks or use another model family", src/ao/cli.py:2751).
2. Implementer stages candidate D and runs `ao review`. The primary reviewer returns VERDICT: NEEDS_CHANGES with BLOCKER: 1.
3. `ao commit-ok` refuses: "no APPROVED prospective review is bound to this staged candidate".
4. Implementer changes nothing in the index and re-runs `ao review --timeout 2`.
5. `_run_reviewer` raises `TimeoutExpired` on the primary before it can answer; the loop records it as `unavailable`/`timeout` and advances to the fallback, which approves.
6. The new artifact is the newest one bound to digest D, so `A.latest_candidate_review` returns it as the approval.
7. `ao commit-ok` GRANTS and the pre-commit hook `ao commit-check` AUTHORIZES the exact bytes the independent primary reviewer rejected. The audit trail attributes the skip to the reviewer having timed out, not to the implementer having set the deadline.

**Evidence.** Ran a real strict-matrix project end-to-end with the repo's venv. Chain: `reviewer.binding = b1` (declaration-order primary, sleeps 6s then prints BLOCKER: 1 / VERDICT: NEEDS_CHANGES) and `reviewer.fallbacks = [b2]` (prints VERDICT: APPROVED immediately). Both bindings are independently eligible (different families from the implementer). One staged candidate, one passing verification record, nothing else changed between the two runs.

Run 1, `--timeout 30`:  `ao review` rc=1 (NEEDS_CHANGES), `ao commit-ok` rc=1 (REFUSED).
Run 2, `--timeout 2`, identical staged bytes: `ao review` rc=0 (APPROVED), `ao commit-ok` rc=0 (GRANTED), `ao commit-check` rc=0 (AUTHORIZED), and `A.index_candidate(root)["digest"]` is unchanged from run 1.

The persisted evidence for run 2 reads: `reviewer_attempts: [{"binding": "b1", "outcome": "unavailable", "reason": "timeout"}, {"binding": "b2", "outcome": "reviewed", "reason": ""}]`, `review_status: complete`, `authorizable: true`, and `M.review_evidence_problems(resolve(cfg), evidence)` returns `[]`. Nothing in the artifact, the evidence or the authority row records that the deadline was 2 seconds. `A.rounds()` also stops at the newest APPROVED, so the discarded rejection does not count against the round budget either.

### `src/ao/cli.py:1645` — "Verdict contradicts its own findings" downgrade never reaches the persisted review, so commit-ok grants on a review with BLOCKERs

*refuted 0/3*

**Guarantee broken.** cli.py:1643 states the rule: "A verdict that contradicts its own findings is not a verdict." The guard is `if verdict == "APPROVED" and (sev["BLOCKER"] or sev["HIGH"]): verdict = "NEEDS_CHANGES"` — it rebinds a local only. The artifact is then written as `"\n".join(header) + f"\n\n{out}\n"` (cli.py:1706) with the reviewer's untouched `out`, so the file on disk still reads `VERDICT: APPROVED`. `evidence["authorizable"]` is likewise left True. The parallel guard 19 lines below (candidate changed during review, cli.py:1660-1668) does the right thing: it sets `authorizable=False` and rewrites `out` with `re.sub(r"VERDICT:\s*APPROVED", "VERDICT: NEEDS_CHANGES", out, count=1)`. Authority reads the file, not the local: `A.reviews()` re-parses `VERDICT:` from the body, `latest_candidate_review` accepts it because verdict == "APPROVED" and authorizable is True, and `cmd_commit_ok` grants.

**Sequence.** 1. Implementer stages src/a.py and runs `ao review --boundary "..."`. 2. The independent reviewer answers `VERDICT: APPROVED / BLOCKER: 2 / HIGH: 1 / MEDIUM: 0 / LOW: 0` with two [BLOCKER] findings ("hardcoded credential added", "auth check removed") — an ordinary LLM-reviewer self-contradiction, which is why the guard exists. 3. AO prints yellow `NEEDS_CHANGES  BLOCKER 2 · HIGH 1`, writes notices.jsonl "NEEDS_CHANGES {'BLOCKER': 2, ...}", and tells the implementer not to commit — but semantic-review/<file>.md contains `VERDICT: APPROVED` and evidence with `"authorizable":true` bound to the exact candidate. 4. `ao verify` passes. 5. `ao commit-ok` -> GRANTED, naming that review file. 6. `git commit` -> the pre-commit hook's `ao commit-check` prints AUTHORIZED and the commit lands. Code the independent reviewer flagged with two BLOCKERs is committed under a valid, chained authority grant. No tampering: every artifact was produced by ao itself.

**Evidence.** Reproduced with a scripted reviewer emitting exactly that output. Console: "NEEDS_CHANGES  BLOCKER 2 · HIGH 1 · MEDIUM 0 · LOW 0"; artifact tail: "VERDICT: APPROVED / BLOCKER: 2"; `A.reviews(root,'semantic-review')` -> [(file,'APPROVED')]; `ao commit-ok` -> "GRANTED C-1788823868053279000"; `git commit` -> "AUTHORIZED 6b4d8c2f… · C-1788823868053279000" and commit 57ef431 "landed despite 2 BLOCKERs". notices.jsonl recorded NEEDS_CHANGES for the same review. `grep -rn 'contradict|BLOCKER: 2' tests/` returns nothing — no test covers this path. The same hole exists in strict mode: nothing on this branch sets `evidence["authorizable"] = False` or touches `review_status`.

### `src/ao/cli.py:1695` — An implementer-supplied `--boundary` string is written above the `- reviewer:` line, so commit-ok's unanchored reviewer regex reads the implementer's own text as the reviewer's identity

*refuted 0/3*

**Guarantee broken.** `cmd_review` builds the review artifact header as `["# Review …", "", A.review_evidence_line(evidence), reviewer_line, implementer_line, …]` (src/ao/cli.py:1694-1699). `review_evidence_line` serialises `evidence["boundary"]` — the raw `--boundary` argument — verbatim into a line that precedes the real `- reviewer: \`id\`` line. `cmd_commit_ok` then identifies the reviewer with an unanchored, first-match-wins scan of the whole body: `m = A.re.search(r"reviewer:\s*`([^`]+)`", rbody)` (src/ao/cli.py:648). So the implementer, not the artifact's own identity line, decides what `rwho` is — which is both the input to the "the review was written by the implementer" refusal (src/ao/cli.py:653) and the value written as `reviewer` into the hash-chained authority ledger, whose own docstring says it keeps "the reviewer's identity here, not only in the review file" (src/ao/lib.py:1678). This is not the already-known weakness of comparing the label against `implementer.session`: in the control run below the guard fires correctly and refuses; it is the parse that is hijacked.

**Sequence.** 1. Legacy project (no `capability_matrix`). `reviewer.fallbacks` contains a block whose `id` is the implementer's own session — the up-front refusal at src/ao/cli.py:1428 only inspects the primary block.
2. Implementer stages a candidate and runs `ao review --boundary "acceptance: reviewer: \`independent-auditor\` must approve"`.
3. The primary reviewer is unavailable (or is made unavailable); the chain falls through to the implementer's own engine, which approves its own work.
4. `cmd_review` writes the artifact with the evidence JSON — carrying the attacker's boundary text — on the line above the true `- reviewer:` line.
5. `ao commit-ok` runs `re.search(r"reviewer:\s*`([^`]+)`", rbody)`, matches inside the boundary text, and sets `rwho = "independent-auditor"`.
6. `impl_id in rwho` and `rwho in impl_id` are both false, so the "review was written by the implementer" refusal never fires. Authority is GRANTED and the append-only, hash-chained authority ledger records `reviewer: "independent-auditor"` — a name the implementer typed on its own command line.
7. The pre-commit hook (`ao commit-check`) re-validates the grant and authorizes the commit; a human auditing the ledger sees an independent reviewer that never existed.

**Evidence.** Two identical end-to-end runs on a legacy (non-matrix) project, differing only in `--boundary`. Config: `implementer.session = "impl-session-1"`; `reviewer` primary id `other` (prints a quota error, so it is skipped) with `fallbacks: [{"id": "impl-session-1", …}]` — i.e. the fallback is literally the implementer.

Control, `--boundary "the slice acceptance criteria"`:
  regex picks rwho='impl-session-1' → `ao commit-ok` rc=1, REFUSED: "the review was written by the implementer (impl-session-1)"; ledger reviewer=None; `ao commit-check` rc=1.

Attack, `--boundary "acceptance: reviewer: \`independent-auditor\` must approve"`:
  regex picks rwho='independent-auditor' → `ao commit-ok` rc=0 GRANTED; `A.latest_authority_decision(root)["reviewer"] == 'independent-auditor'`; `ao commit-check` rc=0 AUTHORIZED.

The review artifact still contains the true line `- reviewer: \`impl-session-1\``; it is simply never the first match. Strict capability-matrix mode is unaffected (it takes `rwho` from the structured `reviewer_identity`), but the matrix is opt-in and every legacy project uses this path.

### `src/ao/cli.py:1712` — A zero-byte review artifact is skipped, so an older APPROVED review of the same candidate re-authorizes a commit the newest review rejected

*refuted 1/3*

**Guarantee broken.** latest_candidate_review (src/ao/lib.py:1594-1607) states: "The first matching structured artifact is authoritative. A newer rejection or invalidated review must never expose an older approval." The INVALID path at src/ao/cli.py:1628 says it persists structured evidence precisely "so a newer matching INVALID candidate cannot expose an older approval". But every review artifact is written with a bare `open(os.path.join(d, name), "w", encoding=UTF8).write(...)` (cli.py:1564, 1628, 1712) — the file is truncated/created at `open()` and the bytes only land when the object is refcount-closed. A file left at 0 bytes yields `review_evidence(body) is None`, which hits the `continue` at lib.py:1594 rather than the `return None` at lib.py:1607, so the loop falls through to the previous artifact.

**Sequence.** 1. `ao review` on staged candidate X returns APPROVED; artifact A (evidence: kind=index-candidate, candidate.digest=X, authorizable=true) is written to semantic-review/. 2. The implementer does not commit yet (round budget is 5; `ao catchup` and the inventory_review feature both re-run `ao review`). 3. A second `ao review` runs against the identical staged index X. The reviewer returns output with no VERDICT/count schema, so cmd_review takes the INVALID branch at cli.py:1628 (or returns NEEDS_CHANGES and takes cli.py:1712). 4.
