# Changelog

Every release of ao, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions are major.minor.patch; while
ao is below 1.0 a minor release may change behaviour, and each such change is listed under
Behaviour changes.

Each line says what a user of ao gets, with the slice that landed it or the backlog row it
closed in parentheses: `#n`, or `part of #n` for a row still open, each kept with its evidence in
[docs/backlog.md](docs/backlog.md). Where a change had neither, its commit is named.
[docs/release.md](docs/release.md) is the checklist for publishing a release.

## [Unreleased]

### New commands

- `ao start [--yes]` walks a repository from nothing to a proven setup: it detects the installed agent CLIs and their model families from the shipped adapters, proposes a cross-family implementer/reviewer pair that satisfies the independence rule (preferring adapters with a measured `verified` level and explaining why each pair is offered), saves the choice to `profiles.json`, asks before running `ao demo`, `ao init`, `ao hooks install`, and `ao prove` (or runs only the steps that need no person under `--yes`), and ends with the steps only a person can take without ever installing software or recording a person's approval itself (ONBOARD).
- `ao ntfy setup|test|status` sets up, tests and checks an outbound `ntfy` phone channel (`ntfy.sh` or self-hosted) in `~/.ao/ntfy.json` (mode `0600`, access token read only from `--token-env NAME`), sending the watchdog's phone alerts over HTTPS POST with `Priority` mapped from the alarm level (`urgent` for red, `high` for orange, `default` otherwise) and recording failed sends without raising into the cycle (NOTIFY-NTFY).
- `ao credits --all` reads every shipped adapter that declares an account ao can reach, one request each, and the local estimate where it declares its transcripts; an adapter that declares neither is named rather than shown another harness's figure or a zero ([telemetry.md](docs/telemetry.md)) (CREDITS-ALL).

### Behaviour changes

- `ao mcp serve` now serves read-only `ao://<project>/board`, `roles`, `ledger` and `decisions` resources, URI templates, and `status`, `land-slice` and `stuck` prompts across MCP `2025-06-18` and `2026-07-28`, and `--project all` serves every project in `ao`'s project registry from a single server while keeping human authority in the CLI (MCP-RES).

### Fixes

- `ao start` now writes the chosen profile to `~/.ao/adapters/profiles.json` only after `ao init` is confirmed, and `ao init` uses the exact implementer/reviewer/architect pair `ao start` selected without letting a project-local `.ao/adapters/profiles.json` override it (ONBOARD-2).
- The landing page's agent support introduction now covers `cloud-generic`'s observation through pull-request polling and Git results alongside the five non-cloud groups and qualifies the `full`/`partial` install-measurement statement for `openai-api`, whose client is tested against a stand-in endpoint while a provider's own answer is proven by an owner's local run, checked in both languages against `src/ao/adapters/*.json` (LANDING-REFRESH-3).
- `ao ntfy` cuts outgoing alert bodies at a UTF-8 character boundary within ntfy's 4,096-byte message limit so multibyte Turkish or emoji alerts under 4,000 characters are never turned into attachments ([alarms](docs/alarms.md)) (NOTIFY-NTFY-2).
- The landing page's agent support introduction now states how each group of packaged adapters is observed (resolved session store read, `call-return` data kept by `ao`, declared transcript shape without a resolved store, `unknown` transcript, or stateless tool reviewer/model backend) and which levels are measured (`full`, `partial`), documented only (`documented`), or `untested`, checked in both languages against `src/ao/adapters/*.json` (LANDING-REFRESH-2).

### Security

- A switch or a review tier that weakens a guarantee is off only on a row ao appended to `.ao/ledger/opt-ins.jsonl` on this machine, as its checkpoint store records: the first row of the chain needs no digest, so an implementer that wrote the config and one row by hand had review off and was granted on verification alone. A row written by hand, or on another machine, now turns nothing off, ao appends nothing after one, and `ao doctor` names it; a checkpoint store `AO_LEDGER_CHECKPOINTS` puts inside the project attests nothing ([features](docs/features.md), OPTIN-ATTESTED).

### Adapters

- `ao init --profile` now offers the three working cross-family, cross-engine presets — `agy-codex` (default: `agy` Gemini 4 Argon implementer with Codex `gpt-6-luna` reviewer), `codex-agy` (Codex `gpt-6-astra` implementer with `agy`'s read-only reviewer agent on Gemini 4 Argon) and `claude-codex` (Claude Code implementer with Codex `gpt-6-luna` reviewer) — and drops `claude-kiro` and `claude-claude`, with every preset's actors verified against the shipped adapters and review-time independence rule (PROFILES).
- `ao mcp serve` speaks the Model Context Protocol revision dated `2026-07-28` beside `2025-06-18`: it answers `server/discover` with `supportedVersions` (`["2026-07-28", "2025-06-18"]`), `capabilities`, `resultType: "complete"` and `_meta["io.modelcontextprotocol/serverInfo"]`, negotiates on each request in `params._meta`, refuses an unknown version in `_meta` with JSON-RPC error `-32022` (`Unsupported protocol version`) naming `supported` and `requested` and malformed `_meta` with `-32602`, and keeps `initialize`-based clients working while answering an unknown version on `initialize` with `2025-06-18` (MCP-2026).

### Under the hood

- The landing page says what ao does now, and a test module keeps it saying that: the page still sold ao as attaching to a running agent, named 15 of the 28 adapters ao ships and left codex and qoder untested after their adapters moved to partial, so its headline, its setup block, its sample run, its adapter table and its two languages are now read from the tree that publishes it - and the headline sentence itself now stands in the package description, the module docstring and the Homebrew formula, which a seventh test holds to it (LANDING-REFRESH).

## [0.6.0] - 2026-10-19

### New commands

- `ao gain [--since 7d]` reads ao's own ledgers and says what it measured - slices landed, what reviews said, where the board stands, what a turn cost and did, each platform's last run and how far HEAD has moved since - with a daily trend; an absent store is named rather than shown as zero, and `--json`, `--slices`, `--sources`, `--quota` and `--all` narrow or widen the reading ([telemetry](docs/telemetry.md#one-surface-ao-gain)) (GAIN).

A move is decided and made on one reading of the board, so a row edited meanwhile is never moved on a judgement made before the edit - ao says the board changed and to run it again - and a board write that fails leaves a line voiding the move it recorded. `ao slice status` says since when a slice is where it is, how it got there, its rounds and its newest review's findings, and `ao slices [--open]` lists every slice, naming a row moved or removed by hand ([slices](docs/slices.md#commands)) (SLICE-LIFECYCLE, SLICE-LIFECYCLE-2).
- `ao review --commits <range> --reviewer <actor> --slice <id>` reviews a landed range again with another reviewer actor of the project's table, held to the rules `ao catchup --reviewer` holds one to, recorded as the slice that landed it and judged against its commit messages ([roles](docs/roles.md), RETRO-REVIEWER).
- `ao ci review` and the repository's `action.yml` have a pull request in any repository reviewed in CI by a model of another family than the one that wrote it, through ao's API reviewer and with no ao setup: the commits it adds to the merge base are reviewed, its title and commit messages read as claims, the verdict and the findings written to the job summary and the step outputs, and `fail-on` decides what fails the job. It reviews and grants nothing, and the author's family is the workflow's statement ([github-action](docs/github-action.md)) (GITHUB-ACTION).
- `ao demo [--keep]` shows the guarantee in about a minute before ao is on a repository of yours: on a scratch project with a home of its own and a stand-in reviewer, a change with a bug is refused by review, `ao commit-ok` and the commit hook, and its fix lands with the trailers that name its grant ([demo](docs/demo.md)) (DEMO).

- The pre-push hook runs the tests the pushed commits touch first, then the whole suite in four processes where pytest-xdist (now in the `dev` extra) is installed - `AO_PREPUSH_WORKERS` sets how many, 0 keeps one - so a push waits about 6 minutes rather than half an hour (PREPUSH-PARALLEL).
- The stand-in hunter in the tests runs Python with -B rather than -I, which dropped PYTHONUTF8 and on Windows left its leads unreadable, and two of the day's tests compare program names and paths as Windows writes them (WINDOWS-TESTS-2).
- The suite's repository guard watches the file an include names before that file exists, where an include added during a run left its file unwatched and a bare flip written into it unseen (SUITE-SPEED-2).
- The marker fingerprint's test forges the identity it reads through a handle, as the fingerprint does, so a Windows runner no longer fails it when a clock tick passes between creating the marker and writing it (WINDOWS-FINGERPRINT-TEST).
- Test runs dispatched on one branch for different runners or interpreters all run, so the release checklist's runs on Python 3.9 and 3.12 no longer cancel each other (CI-DISPATCH-GROUP).
- Findings that needed no code change are held by tests or put right in the documents: the log an architect wake writes is one the log bound trims, each trace line the fuzz invariants read is one a cycle writes, a dead session the wake error does not name is not woken again, the Windows lane's fixtures name no person's home and write an early ao's hook as it wrote it, and a review run's first phase is read from its state (BOUNDED-STORES-2, SCENARIO-FUZZ-2, ESCALATE-DURABLE-2, HOME-FIXTURE, REVIEW-START-DELAY-2, HOOK-V4-2).
- `lib.py` and `cli.py` are split into `src/ao/parts/` as pure moves, each proven byte for byte by `ao split-check` (SPLIT-CHECK and fifteen move-only slices, #44).
- The suite runs on GitHub for every push to main and every pull request (Ubuntu, Python 3.9 and 3.12), on macOS and Windows every week, and a release tag runs it again before anything is published (CI-ON-GITHUB, CI-CONCURRENCY).
- The GitHub release is created only after the PyPI upload, so it never announces a version pip cannot install yet (CI-ON-GITHUB).
- The version is written once, in `src/ao/__init__.py`; `pyproject.toml` and `ao --version` read it (CLI-ROBUST).
- The dependency rule is policy in three tiers - the core on the standard library, optional extras, plugins outside the package - and a test holds the core to the first ([docs/upstream.md](docs/upstream.md)) (DEPENDENCY-TIERS, #82).
- The documents are held to the code: every `ao` command they show parses, and every MCP tool, `.ao` path and setting they name exists (DOCS-COMMANDS, DOCS-NAMES).
- Public files use neutral sample names and carry no machine-local path (NEUTRAL-NAMES, REDACT-LOCAL).
- Faster runs: adapters and settings are read once per run and status asks git without a shell (CLI-STARTUP), and macOS's git stub is skipped in ao and in the suite (SUITE-SPEED).
- The adversarial audit of 2026-09-08 (119 confirmed findings) is kept in [docs/audit/](docs/audit/2026-09-08-adversarial.md), and three architecture decision records in [docs/adr/](docs/adr/README.md).
